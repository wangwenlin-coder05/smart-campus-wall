# 三层架构重构完整指南

## 📋 重构概述

将项目从单一Entity模式重构为标准的三层架构模式（Entity-DTO-VO），所有类统一存放在 `com.wwl.model` 包下。

---

```
com.wwl.model/
├── entity/          # 数据库实体类（严格对应数据表）
│   ├── OrderInfo.java
│   ├── User.java
│   ├── UserAddress.java
│   └── ...
├── dto/             # 请求参数DTO类（接收前端入参）
│   ├── OrderInfoDTO.java
│   ├── UserDTO.java
│   ├── UserAddressDTO.java
│   └── ...
└── vo/              # 视图返回VO类（返回前端展示）
    ├── OrderInfoVO.java
    ├── UserVO.java
    ├── UserAddressVO.java
    └── ...
```

### 第一步：批量生成剩余实体类的DTO和VO

由于项目有19个实体类，建议使用以下两种方式之一：

#### 方式A：使用IDEA插件批量生成（推荐）
1. 安装IDEA插件 "GenerateAllSetter" 或 "DTO Generator"
2. 右键点击Entity类 → Generate → Generate DTO/VO
3. 批量选择字段，自动生成

#### 方式B：手动复制修改（适用于少量类）
1. 复制Entity类到dto/vo目录
2. 修改包名为 `com.wwl.model.dto` 或 `com.wwl.model.vo`
3. 类名改为 `XxxDTO` 或 `XxxVO`
4. DTO添加查询字段，VO添加联表字段

## 📝 各层职责说明

### Entity（数据库实体）
- **包路径**：`com.wwl.model.entity`
- **用途**：严格对应数据库表，仅包含数据库真实字段
- **使用场景**：MyBatis增删改查、数据库持久化
- **禁止**：不包含页面展示字段、联表字段

### DTO（数据传输对象）
- **包路径**：`com.wwl.model.dto`
- **用途**：接收前端请求参数
- **包含字段**：
  - 所有业务字段（与Entity一致）
  - 查询专用字段：`sceneType`、`pageNum`、`pageSize`
- **使用场景**：Controller接收入参、Service处理业务

### VO（视图对象）
- **包路径**：`com.wwl.model.vo`
- **用途**：返回前端页面展示
- **包含字段**：
  - 所有业务字段（与Entity一致）
  - 联表查询字段：`startAddressText`、`endAddressText`
  - 关联查询字段：`orderImageList`、`nickname`、`avatar`等
- **特殊处理**：敏感字段（如id）使用 `@JsonIgnore` 隐藏

## 🔄 数据流转示意

```
前端请求 
  ↓
Controller（接收DTO/Entity）
  ↓
Service（业务处理，可选DTO→Entity转换）
  ↓
Mapper（Entity入库 / VO查询）
  ↓
Service（VO填充额外数据）
  ↓
Controller（返回VO）
  ↓
前端展示
```

## ⚠️ 注意事项

### 1. 字段一致性
- 同含义字段在三层中保持**驼峰命名**和**数据类型**完全一致
- 禁止修改原有字段名和类型

### 2. 日期格式化
- 所有日期字段保留 `@JsonFormat(pattern = "yyyy-MM-dd HH:mm", timezone = "GMT+8")`

### 3. 注解使用
- 统一使用 `@Data` 注解
- VO中敏感字段使用 `@JsonIgnore`
- DTO中移除验证注解（`@NotNull`、`@NotBlank`等）

### 4. 专属字段隔离
- **Entity**：只存数据库真实字段
- **DTO**：存放查询场景、分页等请求参数
- **VO**：存放联表地址文本、图片列表等展示字段

### 5. 禁止混用
- ❌ 不允许在Entity中添加页面展示字段
- ❌ 不允许在VO中添加查询条件字段
- ❌ 不允许在DTO中添加数据库不存在且非查询专用的字段

## 📞 常见问题

### Q1: 为什么要拆分三层？
**A**: 职责分离，提高代码可维护性、安全性和扩展性。

### Q2: 是否所有表都需要拆分？
**A**: 建议核心业务表必须拆分，辅助表可按需处理。

### Q3: 旧代码如何处理？
**A**: 逐步迁移，先保留旧Entity，新代码使用model包，最后删除旧文件。

### Q4: 性能有影响吗？
**A**: 几乎无影响，BeanUtils拷贝性能损耗可忽略。
